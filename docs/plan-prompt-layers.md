# 提示词分层改造思路（未实施）

> 问题：**人格/规矩是纯 txt 全量注入，越加越稀释。**
> 结论：根因不是字数，是**人格没有检索结构**——记忆有锚点图，人格只有一张平铺的纸。
> 本文只写思路和验证方案，**没有动任何代码**。写完日期：2026-10-27。

---

## 一、现状：一个不对称

| 东西 | 存储结构 | 怎么进上下文 |
|---|---|---|
| 记忆（2,345 条） | SQLite 事件表 + **锚点图**（500 锚点 / 13k 边）+ 词法索引（FTS + bigram） | **按需召回**，≤1,200 token |
| 知识（462 条） | JSON + 挂锚点 | 按锚点**按需取** |
| **人格**（2,227 字 / 约 36 条规矩 / 11 节） | **纯 txt** | **每句全文注入** |
| 说话规矩（1,094 字） | 纯 txt | 每句全文追加 |

**记忆有索引，所以只取相关的；人格没有索引，所以只能全量塞。** 这就是稀释的根源。

### 现在的体积账（每次请求都要重发）

| 块 | 字数 | ≈ token |
|---|---|---|
| 人格 `persona.md` | 2,227 | ~1,480 |
| 说话规矩 `speech-rules.md` | 1,094 | ~730 |
| 底线 FLOOR | ~150 | ~100 |
| 【我】`self.md` | 325 | ~215 |
| 记忆块（上限） | — | 1,200 |
| 工具清单（74 个名字） | 863 | ~575 |
| 历史（≤30 条） | — | ~1,000 |
| 场景 / 额度 / 谁是谁 / 统计 | ~700 | ~470 |
| **合计** | | **≈ 5,800** |

人格 + 说话规矩 ≈ **2,200 token，占系统提示的 37%**，而且每一轮工具调用都重发一次。

## 二、根因：稀释是结构问题，不是字数问题

| 毛病 | 具体表现 |
|---|---|
| **散文段落，不是清单** | 规矩混在叙述里，模型没有"条目感"，越长的段落里单条越弱 |
| **重复** | "别编造"在 persona 里出现两次，代码里还有 `looksFabricated` 守卫兜着 |
| **身份与操作规则混住** | "你是谁""怎么回群消息""谁能解决问题"三类东西挤在一个文件 |
| **没有优先级声明** | 人格在开头、说话规矩追加在末尾，冲突时谁赢没人说 |
| **不分场景全量注入** | 走神时也在读"群里怎么接话" |

---

## 三、三种存储结构，对"人格"合不合适

| 结构 | 能不能解决稀释 | 代价 | 判断 |
|---|---|---|---|
| **txt 全量**（现状） | ❌ 线性稀释：加一条，其它每条的存在感就薄一分 | 无 | 现状 |
| **图 / 锚点索引** | ✅ 拆成卡片、挂场景锚点，每轮只取相关的 8–12 条 | 要写召回（可复用 `anchors.ts`） | **最合适** |
| **向量（embedding）** | ⚠️ 语义召回好，但三个问题 | 高 | **不适合人格** |

**为什么向量不适合人格：**

1. 破坏零依赖（要本地 embedding 模型或外部 API）
2. 人格是**约束**，不能靠"相似度"保证命中——"不许编造过去"不该等它跟这句话语义相近才被想起来
3. 每轮要算向量，还多一层不透明的失败模式

> 向量可以留给**知识库**（462 条、内容型、允许"想不起来"）。人格不行。

## 四、目标结构：两层

```
第一层：常驻核心（txt，永远注入）
   底线 4 条 + 硬约束 ~20 条
   ≤ 600 字
   —— 赌不起的东西放这儿：不编造 / 不认领别人的话 / 动手前先想

第二层：情境规则（图索引，按需召回）
   其余 ~30 条，拆成卡片，每条挂 1–3 个场景锚点：
     「接话」「问往事」「被质疑」「群里」「走神」「改自己」「被夸」「认错」
   当前这句话 → 匹配场景 → 激活扩散 → 取 top 8–10 条（≤ 600 字）
   —— 直接复用记忆那套 anchors.ts，不需要发明新算法
```

### 卡片长这样（还是同一个 txt，只是分段）

```md
## 场景：认错
- 说错了就直接说错在哪，一句「是我听岔了」就够，接下去往下说。

## 场景：被质疑 · 群里
- 先分类：是这一句的事，还是说话方式的事？句子改十遍，毛病还在。

## 场景：动手之前
- 任何思考和动作前先想一遍：有没有改进方法的方法？
```

渲染顺序固定：`底线 → 常驻核心 → 本次召回的情境规则 → 风格偏好`。
并在最前面加一句优先级声明：**冲突时从上往下，上面的优先。**

### 预期效果

| | 现在 | 目标 |
|---|---|---|
| 人格相关注入 | ~2,200 token | ~900 token（常驻 600 + 召回 300） |
| 相关规矩命中 | 全在（但被稀释） | 相关的一直在，无关的不占位 |
| 加新规矩的边际成本 | 每条都稀释其它所有条 | 只影响它自己那个场景 |

## 五、三个必须一起想清楚的问题

### ① 漏召回 = 行为事故（最大风险）

一条该用的规矩没被召回，等于它不存在，**而且不会报错**。

缓解：先用对照测试量出来（见第六节）。人工判定该用哪条 vs 实际召回，算漏召回率。**低于某个可接受值之前不上线。**

### ② 缓存：不额外损失

一开始担心"动态注入毁前缀缓存"，查过之后不成立：

- **记忆块本来就是每句变的**，系统提示每句都不同，跨消息的缓存命中早就没有；
- 现在的命中（约 63%）主要来自"同一次回复内多轮重复"和工具定义。

所以人格做检索，**不会比现在更差**。

### ③ 常驻核心也会慢慢长大

需要一条晋升/降级规则：常驻超 30 条，就把"最近 30 天一次都没触发"的降级回情境池。
`self_status` 已经给了她字数，再加一行"常驻多少条"就够她自己维护。

## 六、验证方案（先测再改）

**对照组测试**：

1. 抽 100 条真实对话（私聊 + 群聊 + 走神各一批）
2. 人工标出"这句话该用哪几条规矩"
3. 跑召回，记录实际取到的条目
4. 指标：
   - **漏召回率** = 该用没取到的条数 / 该用的总条数
   - 注入 token 降幅
   - 误召回（取到无关规矩）比例

**通过的线**：漏召回率接近 0（硬约束那 20 条本来就不参与召回，所以只测情境池）。

## 七、实施步骤（每步都能停）

| 步 | 做什么 | 可回滚点 |
|---|---|---|
| **1** | 只给现有规矩打场景标记（`## 场景：xxx`），**不改任何逻辑** | 纯注释，删掉就回去 |
| **2** | 加召回代码，**影子模式**：照常全量注入，但把"如果按场景召回会取到哪几条"记进日志 | 只多写日志 |
| **3** | 对照测试通过后，切换成"常驻 + 召回" | 一个开关切回全量 |

---

## 八、明确不做的事

| 不做 | 为什么 |
|---|---|
| 人格向量检索 | 约束不能靠相似度命中；破坏零依赖 |
| 按场景砍掉底线 | 底线永远全量，不进召回池 |
| 把人格切成多个文件 | 那是文件结构，不解决稀释；她改自己还得跨文件 |
| 动态丢弃"说话规矩"全文 | 说话规矩是高频规则，先留在常驻层，观察后再拆 |

## 九、和已有决定的关系

- **2026-10-27 已经加的一条**：`persona.md` 的【动手之前】——「任何思考和动作前先想一遍：有没有改进方法的方法？」。
  它现在是纯提示词，**没有触发机制**；本文的"常驻核心"应该把它收进去。
- **卡榫（工具环里的失败检测）**：上一次讨论里决定不做。它和本文是两条独立的路——
  卡榫是"机制"，分层是"结构"。**结构能延缓稀释，机制才能保证执行。**
